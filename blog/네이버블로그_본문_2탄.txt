■ 들어가며

지난 글에서는 카톡 메시지를 복사하고 단축어를 한 번 누르면 구글 캘린더에 일정이 들어가는 도구를 만들었습니다. 제 계정에서 테스트를 마치고 친구에게 넘기려고 하자마자 첫 요청이 왔습니다.

"근데 공지가 글보다 이미지로 더 많이 와."

현장 일정표는 엑셀로 만든 표를 캡처하거나 PDF로 뽑아서 단톡방에 올리는 경우가 대부분이었습니다. 복사할 텍스트가 없으니 1탄의 방식으로는 쓸 수가 없었습니다. 그래서 2탄에서는 이미지, 일정표, PDF를 읽게 만든 과정과, 표를 '추정하지 말고 그대로' 옮기게 하느라 고친 규칙들을 정리합니다.

이번에 바꾼 것을 먼저 요약하면 이렇습니다.
• 카톡 이미지, 캡처, 사진을 공유 시트로 넘기면 분석
• 일정표를 읽는 규칙 추가 (CALL TIME, 빈 시간 칸, "~22시" 마감, * 보충 문구, 빨간색 강조)
• PDF 일정표 지원, 시간 초과를 피하려고 페이지별 병렬 분석
• 일정이 많을 때 미리보기가 화면을 넘치는 문제 해결


■ 친구 등록부터

1탄 끝에서 만든 '캘린더 공유 방식'을 처음 실제로 써 봤습니다. 순서는 이랬습니다.

1. 친구가 업무용 캘린더를 새로 만들고, 제 계정에 '일정 변경' 권한으로 공유
2. 웹앱 주소(등록 페이지)를 열고 초대 코드와 캘린더 ID 입력 → 개인 코드 발급
3. 제 단축어를 복제해 secret 칸을 '가져오기 질문'으로 바꾸고 iCloud 링크로 전달
4. 친구는 단축어를 추가할 때 개인 코드만 붙여넣기

캘린더 ID는 구글 캘린더 웹 → 해당 캘린더 설정 → '캘린더 통합' 항목에 있습니다.

배포에서 한 번 헷갈린 부분이 있습니다. Apps Script에서 '새 배포'를 만들면 웹앱 주소가 바뀌어서, 이미 나눠 준 단축어가 전부 끊깁니다. 코드를 고친 뒤에는 기존 배포를 수정해야 주소가 유지됩니다. clasp로는 이렇게 합니다.

[소스코드]
npx @google/clasp push --force
npx @google/clasp deploy -i <기존 배포 ID> -d "변경 내용"
[소스코드 끝]

--force 없이 push하면 매니페스트 확인 단계에서 "Skipping push"만 출력되고 아무것도 올라가지 않는 경우가 있었습니다.


■ 구현 1. 이미지 받기

Claude API는 이미지를 base64로 받아서 글자와 표를 읽을 수 있습니다. 그래서 서버에서 할 일은 단축어가 보낸 base64를 이미지 블록으로 바꿔 메시지 앞에 붙이는 것뿐입니다.

[소스코드 - JavaScript]
const userContent = images.map(function (img) {
  return { type: 'image', source: { type: 'base64', media_type: img.mediaType, data: img.data } };
}).concat([{ type: 'text', text: text }]);
[소스코드 끝]

단축어에서 여러 장을 보낼 때는 쉼표(,)로 이어 붙인 문자열 하나로 보냈습니다. base64에는 쉼표가 나오지 않아서 구분자로 쓰기 좋습니다. 처음에는 줄바꿈으로 나눴는데, 단축어의 Base64 인코딩이 설정에 따라 중간에 줄바꿈을 넣는 바람에 이미지가 쪼개졌습니다. 지금은 쉼표로만 나누고 공백과 줄바꿈은 지웁니다.

이미지 형식은 base64 앞부분으로 판별합니다.

[소스코드 - JavaScript]
function imageMediaType_(b64) {
  if (b64.indexOf('/9j/') === 0) return 'image/jpeg';
  if (b64.indexOf('iVBORw0KGgo') === 0) return 'image/png';
  if (b64.indexOf('R0lGOD') === 0) return 'image/gif';
  if (b64.indexOf('UklGR') === 0) return 'image/webp';
  if (b64.indexOf('JVBERi0') === 0) return 'application/pdf';
  return '';
}
[소스코드 끝]

아이폰 사진 기본 형식인 HEIC는 Claude가 받지 않습니다. 그래서 단축어에서 JPEG로 변환해서 보내게 했고, 한 번에 5장까지로 제한했습니다.


■ 구현 2. 단축어에 이미지 경로 추가

단축어는 '이미지가 들어왔으면 이미지 경로, 아니면 기존 텍스트 경로'로 나눴습니다. iOS 버전에 따라 동작 이름이 달라서 실제 화면 기준으로 적습니다.

1. 단축어 설정 → 공유 시트에서 받기 : 텍스트, 이미지, 파일 (화면에는 '이미지 및 18개' 같은 식으로 표시)
2. 단축어 입력에서 이미지 가져오기
3. 조건문 : [이미지] 값을 가지고 있음 인 경우
   - 각각 반복 (화면에는 '이미지의 각 항목 반복')
     · 이미지 크기 조절 : 반복 항목, 최장 가장자리 2000
     · 이미지 변환 : JPEG, 메타데이터 보존 끔
     · Base64 인코딩 : 줄 바꿈 없음
   - 반복 종료
   - 텍스트 결합 : 반복 결과, 사용자 지정 구분자 "," → 변수 '이미지목록'
4. 그렇지 않은 경우 : 변수 '본문' = 단축어 입력
5. URL 콘텐츠 가져오기 : 필드에 images = 이미지목록 추가

여기서 막혔던 곳이 몇 군데 있습니다.
• '반복'과 '각각 반복'이 따로 있습니다. 목록을 하나씩 처리하는 것은 '각각 반복'입니다. '반복'은 횟수를 정해서 돌립니다.
• 조건문의 입력이 '이미지'가 아니라 '앨범' 같은 속성으로 잡히는 경우가 있습니다. 눌러서 이미지로 바꿔야 합니다.
• 크기 조절을 '너비 2000'으로 두면 세로로 긴 캡처가 엄청 길게 남습니다. '최장 가장자리'로 해야 긴 쪽이 2000으로 맞춰집니다.
• URL 콘텐츠 가져오기의 필드는 오른쪽 파란 '>'를 눌러야 펼쳐집니다.

이제 카톡에서 이미지를 크게 띄우고 공유 → 단축어를 누르면, 10~30초 뒤에 미리보기가 뜹니다.


■ 구현 3. 일정표를 "추정하지 말고 그대로" 읽게 하기

이미지 분석은 바로 돌아갔는데, 실제 일정표를 넣어 보니 결과가 미묘하게 틀렸습니다. 테스트한 일정표는 공연 철수 날의 표였습니다.

[표 구조 예시]
CALL TIME | 전체 09시
9시       | 안전교육 <철수인원>          ← 빨간 배경
(빈칸)    | 조명 ... 철수 후 다운스테이지 시작
(빈칸)    | 소품 및 의상 이동 등
14시      | 양주창고 이동 시작(벤치, 가로등 세트팀에 같이 보내기)  ← 괄호는 빨간 글씨
(빈칸)    | 백석창고 이동: ... / 신관창고 이동: ... / 엠씨어터 이동: ...
          | *백석창고 이동: 제작팀 17시 출발 예정
          | *바닥 극장 보관
~22시     | 극장 장비 및 막종류 원위치 및 청소 등
[표 구조 예시 끝]

처음 결과의 문제는 이랬습니다.
• 빈 시간 칸을 보고 중간 시간을 지어냈습니다.
• "제작팀 17시 출발 예정"을 17시 일정으로 따로 만들었고, 그 문구가 엠씨어터 줄에 붙었습니다.
• 끝나는 시간이 없는 일정에 끝 시간을 추측해 넣었습니다.

1탄의 프롬프트에 "확실하지 않으면 추측하되 확신도를 low로" 라는 규칙이 있었는데, 표에서는 이 규칙이 오히려 문제였습니다. 그래서 원칙부터 바꿨습니다. "원문(텍스트·이미지)에 적힌 정보만 쓴다. 적혀 있지 않은 시간, 장소, 수량은 만들어 넣지 않는다."

그리고 일정표 전용 규칙을 추가했습니다.
• 날짜 칸이 여러 행에 합쳐져 있으면 그 날짜는 해당 행 전체에 적용한다.
• 시간이 적힌 행이 새 일정의 시작이다. 시간 칸이 빈 행은 바로 위 시간 행의 일정에 속한다.
• CALL TIME은 별도 일정을 만들지 않고, 그날 첫 일정 메모 첫 줄에 "콜타임 09:00"으로 적는다.
• 셀 안에 적힌 시각(17시 출발 예정)은 일정 시작 시간으로 쓰지 않고 메모에 둔다.
• 소제목(백석창고 이동, 신관창고 이동)이 여러 개면 메모에서 소제목별로 줄을 나눈다. "*" 보충 문구는 가리키는 소제목 줄에 붙이고, 서로 섞지 않는다.
• 메모의 줄 순서는 표의 위→아래 순서를 따른다.

친구에게 결과를 보여 주고 나서 고친 규칙도 있습니다.

"~22시"는 마감이었습니다
처음에는 "~22시"를 '14시부터 22시까지'인 별도 일정으로 만들었습니다. 그런데 표에서 이 행의 뜻은 '22시까지만 끝내면 된다'였습니다. 이제는 별도 일정을 만들지 않고, 위 일정 메모의 맨 아래 줄에 "~22시까지 완료: ..."로 넣고 그 일정의 끝을 22:00으로 둡니다. 표에서 맨 아래에 있으니 메모에서도 맨 아래입니다.

제목은 원문 그대로
"양주창고 이동"으로 줄였더니 "14시에 '시작'해야 한다는 뜻이 빠졌다"는 피드백을 받았습니다. 이제 제목은 그 행의 본문을 원문 그대로 쓰고, 뒤에 붙은 괄호 문구만 메모로 옮깁니다.

빨간색은 중요 표시
표에서 빨간 글씨나 빨간 배경은 '꼭 챙길 것'이라는 뜻이었습니다. 스키마에 important 필드를 추가하고, 이 값이 true면 캘린더 일정 색을 빨간색으로 바꿉니다. 메모에서는 해당 줄 앞에 ❗를 붙입니다.

[소스코드 - JavaScript]
// 스키마
important: { type: 'boolean', description: '원문에서 빨간색(글씨·배경)으로 강조된 내용이 이 일정에 있으면 true' },

// 일정 만들 때
if (a.important) ev.setColor(CalendarApp.EventColor.RED);
[소스코드 끝]

메모 끝에 붙던 "(11/11)"
메모에 "바닥 극장 보관 (11/11)"처럼 의미를 알 수 없는 날짜가 붙어 있었습니다. 메모를 덧붙일 때 처리 날짜를 메모 끝에 붙이던 코드 때문이었습니다. 1탄에서는 메모가 한 줄이라 문제가 없었는데, 여러 줄이 되면서 마지막 줄의 내용처럼 보였습니다. 지금은 새 일정에는 날짜를 붙이지 않고, 기존 일정에 메모를 더할 때만 "[11/11 추가]"를 별도 줄로 넣습니다.

끝 시간만 바뀌는 경우
"~22시"를 반영하면 기존 14시 일정의 시작은 그대로이고 끝만 바뀝니다. 그런데 기존 코드는 시작 시간이 있을 때만 시간을 고쳐서, 끝 시간 변경이 조용히 무시되었습니다. 끝만 있는 update도 처리하게 고쳤습니다.

고친 뒤의 미리보기는 이렇게 나옵니다.

[소스코드]
1. 안전교육 <철수인원> · 11/9(월) 09:00   ❗중요(빨간색)
   콜타임 09:00
   ❗안전교육 <철수인원>
   조명 #34, 4sus, #24, 3sus 까지 철수 후 다운스테이지시작
   ...
2. 양주창고 이동 시작 · 11/9(월) 14:00~22:00   ❗중요(빨간색)
   ❗벤치, 가로등 세트팀에 같이 보내기
   백석창고 이동: ... (제작팀 17시 출발 예정)
   신관창고 이동: ...
   엠씨어터 이동: 트러스 머리막 2ea
   *바닥 극장 보관
   ~22시까지 완료: 극장 장비 및 막종류 원위치 및 청소 등
[소스코드 끝]


■ 구현 4. PDF와 시간 초과

다음 요청은 PDF였습니다. 따로 고치지 않아도 될 줄 알았습니다. 단축어가 PDF를 받으면 '이미지 가져오기'에서 페이지별 이미지로 바꿔 주기 때문입니다. 실제로 3페이지 일정표 PDF를 넣자 이미지 경로는 탔지만, 단축어에 "요청한 시간이 초과되었습니다"가 떴습니다.

PC에서 같은 요청을 보내 시간을 재 보니 원인이 보였습니다.

• 3페이지 표 안에 일정이 60개 넘게 있었습니다.
• 한 번에 분석하면 52초가 걸렸습니다. 아이폰 단축어의 URL 요청은 약 60초를 넘기면 끊기는데, 업로드 시간까지 더하면 넘어갑니다.
• effort를 medium에서 low로 낮춰도 69초로 오히려 느렸습니다. 시간 대부분이 '생각'이 아니라 일정 60개를 JSON으로 써 내려가는 데 들어갔기 때문입니다.

결과를 쓰는 양을 줄일 수는 없으니, 나눠서 동시에 처리하기로 했습니다. 첨부가 여러 개면 첨부마다 Claude를 따로 부르고, Apps Script의 UrlFetchApp.fetchAll로 요청을 동시에 보낸 뒤 결과를 합칩니다. 걸리는 시간이 '전체 합'에서 '가장 오래 걸린 한 페이지'로 바뀝니다.

[소스코드 - JavaScript]
function callClaude_(messagesText, events, cfg, images) {
  if (images.length <= 1) {
    return parseClaudeResponse_(UrlFetchApp.fetch(API_URL_, claudeRequest_(messagesText, events, cfg, images, '')));
  }
  const requests = images.map(function (img, i) {
    const hint = '첨부 ' + images.length + '개 중 ' + (i + 1) + '번째만 보내졌다. 이 첨부 내용만 작업으로 만든다.' +
      (i > 0 ? ' 카톡 메시지(텍스트)는 1번째 첨부 쪽에서 처리한다.' : '');
    return claudeRequest_(messagesText, events, cfg, [img], hint);
  });
  const all = [];
  UrlFetchApp.fetchAll(requests).forEach(function (res) {
    parseClaudeResponse_(res).forEach(function (a) { all.push(a); });
  });
  return dedupeActions_(all);   // 같은 제목+시작 시간, 같은 기존 일정 수정은 하나만 남김
}
[소스코드 끝]

나눠서 보내니 새 문제가 두 가지 생겼습니다.
• 2페이지에 빨간 테두리 박스가 쳐져 있었는데, 그 박스 안 일정 2개만 읽고 나머지를 빠뜨렸습니다. 박스를 '여기만 보라'는 표시로 받아들인 것입니다. "빨간 테두리나 형광 칠은 강조일 뿐, 표 전체를 처리한다"는 규칙을 넣었습니다.
• "휴식" 행이 모두 일정으로 들어왔습니다. 쉬는 시간만 적힌 행은 만들지 않게 했습니다.

이렇게 고친 뒤 3페이지에서 일정 65개가 빠짐없이 나왔고, PC 기준으로 33~52초가 걸렸습니다. 같은 요청도 실행할 때마다 시간이 꽤 달랐습니다. 아이폰에서 같은 PDF를 공유해 보니 이번에는 시간 초과 없이 미리보기까지 떴습니다.

참고로 PDF를 이미지로 바꾸지 않고 그대로 보내는 경로(document 블록)도 서버에 넣어 두었습니다. 텍스트를 복사할 수 있는 PDF는 글자를 직접 읽어서 더 정확할 수 있습니다. 다만 지금 단축어는 PDF를 이미지로 바꿔서 보내기 때문에 실제로는 위의 병렬 처리를 탑니다.


■ 구현 5. 미리보기가 화면을 넘칠 때

시간 초과를 넘기고 나니, 이번에는 미리보기 창에서 아무것도 누를 수 없었습니다. 단축어의 '메뉴에서 선택'은 위쪽 설명 글을 스크롤하지 못합니다. 일정 65개의 미리보기가 화면을 다 덮어서 반영/취소 버튼이 화면 밖으로 밀려났습니다.

단축어는 그대로 두고, 서버에서 미리보기 길이가 900자를 넘으면 짧은 목록으로 바꿔 보내게 했습니다.

일정 하나를 한 줄로, 최대 12줄까지 보여 줍니다. 메모를 빼는 것은 미리보기 화면에서뿐이고, 캘린더에는 메모까지 모두 들어갑니다. 일정이 몇 개뿐일 때는 전처럼 메모까지 자세히 나옵니다.

멈춘 창을 닫을 때는 다이나믹 아일랜드의 단축어 아이콘을 눌러 정지하면 됩니다.


■ 테스트할 때 쓴 방법

규칙을 고칠 때마다 아이폰으로 이미지를 공유해 보는 건 느렸습니다. 그래서 같은 이미지를 PC에서 웹앱에 직접 보내고, parse만 호출해 미리보기를 확인했습니다. parse는 캘린더를 바꾸지 않으니 몇 번이고 돌려도 안전합니다.

[소스코드 - bash]
node -e '/* 이미지 파일을 base64로 읽어 {secret, action:"parse", images} JSON 파일 생성 */'
time curl -sL -H "Content-Type: application/json" --data-binary @req.json "<웹앱 주소>"
[소스코드 끝]

curl에서 -X POST와 -L을 같이 쓰면 구글의 리다이렉트를 따라갈 때 411 Length Required 오류가 납니다. --data-binary만 주면 알아서 POST로 보내고 리다이렉트도 제대로 따라갑니다. 시간을 잴 때는 time을 앞에 붙였습니다.

캘린더에 이미 같은 날 테스트 일정이 있으면 새 일정 대신 '변경'으로 나옵니다. 깔끔하게 다시 보려면 테스트 일정을 지우고 돌리는 게 편했습니다.


■ 마치며

이제 텍스트, 카톡 캡처, 엑셀 일정표 사진, PDF까지 같은 단축어 하나로 들어갑니다. 이번 작업에서 시간이 가장 많이 든 곳은 이미지 처리 코드가 아니라 '표를 사람이 읽는 방식대로 읽게 하는 규칙'이었습니다. 빈 칸이 무슨 뜻인지, "~22시"가 끝 시간인지 마감인지, 빨간색이 무슨 뜻인지는 그 표를 쓰는 사람만 압니다. 실제 사용자에게 결과를 보여 주고 고치는 과정을 몇 번 반복해야 했습니다.

남은 과제도 있습니다.
• 시간 초과 여유가 아직 크지 않습니다. 3페이지 PDF는 아이폰에서 통과했지만, PC에서 잰 시간이 최대 52초로 60초 한계에 가깝습니다. 더 큰 PDF가 오면, 서버가 분석을 먼저 받아 두고 단축어가 몇 초 뒤에 결과를 다시 가져오는 방식으로 바꿔야 합니다.
• 표에 끝 시간이 없는 일정은 여전히 1시간짜리로 들어갑니다. 구글 캘린더는 끝 시간이 꼭 있어야 해서, 0분짜리 일정으로 바꿀지 고민 중입니다.
• 매일 반복되는 "분장시작: 개인 분장시간표 확인!" 같은 행이 날마다 종일 일정으로 들어갑니다. 반복 안내 문구를 어떻게 다룰지 정해야 합니다.
